## 第一代壳 DEX整体加固

第一代壳主要是对dex/apk文件整体加密，然后**自定义类加载器动态加载**dex/apk文件并执行。在动态加载dex/apk文件的时候有落地加载和不落地加载，落地加载就是通过`DexClassLoader`从**磁盘**加载dex/apk文件，不落地加载就是通过`InMemoryDexClassLoader`从**内存**中加载dex/apk文件。

### DEX文件结构

![](/images/安卓壳/image-3.png)

不需要死记，也不能只看一遍 

说明：

> 1. Magic（标识符）：`64 65 78 0A`（即 `dex\n`）。脱壳时如果魔数不对，或者变成了 `dey\n`（某些壳的特征），你就知道 DEX 被篡改或加密了。
> 
> 2. Checksum（校验码）与 Signature（签名）：图里提到了“设计两个校验码的目的”。脱壳修复必考。你 **Dump 出来的 DEX 如果修改了任何字节，这两个值必然对不上，导致 Android 系统拒绝加载。脱壳后需要用脚本重新计算这两个值**。
> 
> 3. header\_size（文件头长度）：**标准是 ****`0x70`****（112字节）。如果壳把文件头扩展了（比如塞入了自己的 Hook 信息），你需要把它改回 ****`0x70`****。**
> 
> 4. map\_off（map数据基地址）：脱壳修复的核心指南针。Map列表记录了 DEX 里所有数据段的类型、大小和偏移。如果壳破坏了各类 `ids` 的偏移，你可以通过解析 `map_off` 逆向找回真实的结构。
> 
> 5. 各类 IDs 段（String, Type, Proto, Field, Method, Class）：图里下方的那些 `_size` 和 `_off`。壳经常会把方法抽取（Method 对应的代码段被抹零或指向壳的代码），修复时你需要定位这些列表，把抽走的方法体还原回去（比如 FART、Youpk 脱壳机的原理）。
> 
> 



> 加固（壳）的本质，通常是对原始 DEX 进行加密、隐藏或抽取（比如抽走方法体 `nop` 掉，或者把 DEX 整体加密保存在壳的 DEX 或 so 库中）。
> 
> - 脱壳（内存Dump）：当你从内存中把解密后的 DEX Dump 出来时，常常发现它跑不起来（比如提示 `Unable to open dex file` 或解析错误）。这是因为壳在加载时修改了文件头，或者 Dump 出来的数据不完整。
> 
> - 修复（Fix）：你需要手动或通过脚本修复这个 DEX。修复的核心依据，就是上述这些字段（尤其是 `file_size`、`checksum`、`signature`、`map_off` 以及各类 `ids_off`）。
> 
> 

### 一代壳实现原理

app**启动流程**：

![](/images/安卓壳/image-1.png)

这张图展示的是安卓手机开机启动一个 App 时，系统底层（`ActivityThread`）是如何创建并运行你的 App 的。（标准执行顺序）

`Application.attach()`：当 `ActivityThread` 决定要实例化你的 App 时，它会先通过反射创建 `Application` 对象，然后立刻调用它的 `attach()` 方法。



**加固厂商如何利用上述固定的系统调用链路，实现加密代码的加载呢？**

加壳后，`AndroidManifest.xml` 中配置的 **`Application` 被替换成了壳的 Application**。以下步骤全部发生在壳的 Application 代码中：

#### 静态结构

1. 加壳状态：加固厂商将原始真实的 APK 文件进行加密，并**将这段密文附加在壳 APK 的 Dex 文件末尾。**

2. 执行目标：当壳 APK 运行时，必须先将这段密文解密，恢复出原始 APK（或 Dex 文件），然后将其动态加载到内存中。

#### 动态运行流程

1. 系统的固定调用链：

    - 系统进程（`ActivityThread`）在 `handleBindApplication()` 方法中，会通过 `Instrumentation.makeApplication()` 实例化 App 的 `Application`。

    - 实例化后，系统会严格按照以下顺序调用方法：`attach()` \-\> `attachBaseContext()` \-\> `onCreate()`。

2. 壳的介入点 1：重写 **`attachBaseContext()`**

    - 为什么选这里：“**壳代码需要最早获取到加壳apk的执行时机**”。在 Android Java 层，`attachBaseContext()` 是整个 App 进程中最早拿到 `Context`（上下文）且可以执行自定义代码的地方（早于 `onCreate`）。

    - 壳的具体操作：**壳的 ****`Application`**** 重写了此方法**。在此方法内，**壳执行**以下核心逻辑：

        - 解密：将附加在 Dex 尾部的原 APK 解密。根据实现策略，可以将其写入磁盘文件（落地加载），也可以直接以字节流形式留在内存（不落地加载）。

        - 动态加载：使用 `DexClassLoader` 或 `PathClassLoader` **加载解密后的原 APK**。

        

        > 为了理解后续的替换，最好具备一些前置知识：
        > 
        > 为了**让系统能找到真实的代码**，壳必须对系统底层的对象进行“篡改”。这就涉及到一个核心的类：`LoadedApk`。
        > 
        > “原先只能识别壳的代码”的意思是：系统当前挂载的 `ClassLoader`，它的**搜索范围只局限于壳的 APK 文件**。
        > 
        > `mClassLoader` 变量，就是前面提到的“只能识别壳代码”的类加载器。
        > 
        > 

        - 替换 `mClassLoader`：系统原本的 `ClassLoader` 只能识别壳的代码。壳通过反射机制，获取当前进程的 `LoadedApk` 对象，将其内部的 ****`mClassLoader`**** 引用替换为刚刚加载原 APK 的 **`ClassLoader`**。这样，系统后续去加载任何一个类时，都能顺着新的 `ClassLoader` 在解密后的原 APK 中找到。

3. 壳的介入点 2：重写 **`onCreate()`**

    - 壳的具体操作：在 `attachBaseContext()` 完成解密和替换后，系统接着调用壳的 `onCreate()`。此时，壳通过反射（Reflection）找到并**实例化原 APK 中真实的 ****`Application`**** 类**。

    > 我们先理清一个前提：系统不认识真实的 **`Application`**。
    > 
    > 用户在 `AndroidManifest.xml` 里配置的 `android:name` 已经被加固工具改成了壳的 `Application`（比如叫 `StubApp`）。系统启动 App 时，只认死理，它只会去实例化并调用 `StubApp` 的 `onCreate`。
    > 
    > 这就产生了一个致命问题：
    > 真实的开发者**在原版 ****`Application`**** 的 ****`onCreate`**** 里写了很多初始化代码**（比如 `Fresco.initialize()`、`Bugly.init()`、初始化数据库、配置全局变量等）。如果壳不管这件事，这些核心初始化代码就永远不会被执行。 你的 App 跑起来就会各种崩溃、黑屏或者报空指针异常。
    > 
    > 

    

    - 生命周期代理：壳手动调用真实 `Application` 的 `attach()` 和 `onCreate()` 方法。至此，真实业务代码接管了进程。

总结被AI全肯定了 然后他还是稍微帮我润色了一下：

壳的 `Application` 重写了 `attachBaseContext` 方法：在这里，它先解密原 APK，然后创建了一个能加载整个原 APK 的新加载器，并用反射把系统原本只能加载壳的 `mClassLoader` 替换掉了。
接着，壳重写了 `onCreate` 方法：在这里，它通过反射去实例化真正的 `Application` 类。

![](/images/安卓壳/QQ_1792402606904.png)



简单来说：

一代壳是最早、最简单的一代。做法：将整个原始 `classes.dex` 加密后藏进 APK（通常在 `assets/` 中，或者被放入 `.so` 中），APK 中的 `classes.dex` 只是用于加载的程序。在运行时，该程序会一次性解密整个真正的 DEX 文件，然后使用 `DexClassLoader` （或是更底层的 `DexFile` / `InMemoryDexClassLoader` ）将其全部加载到内存中。

```Java
一代壳的内存状态：
assets/encrypted.dat  ──解密──▶  [完整明文 DEX 摊在内存]  ← 一整块、连续、完整
                                        │
                                   DexClassLoader 加载
                                        │
                                   真 App 跑起来
```

```Java
        super.onCreate(savedInstanceState);
```

```Java
package com.example.pack_test_one; // 包名，说明这是项目的主包

// 导入各种安卓内置的类，**用来画界面、打日志等**
import androidx.appcompat.app.AppCompatActivity;
import android.os.Bundle;
import android.util.Log;
import android.widget.TextView;
import com.example.pack_test_one.databinding.ActivityMainBinding;

// MainActivity 继承自 AppCompatActivity，**说明这是一个带界面的“页面”**
public class MainActivity extends AppCompatActivity {

    // 【静态代码块】：**在类被加载时，最先执行且只执行一次**
    static {
        // 核心：加载名为 "pack_test_one" 的 C/C++ 动态链接库（对应 libpack_test_one.so 文件）。
        // 这说明这个 App 里面有 Native 代码（C/C++ 写的代码）。
        System.loadLibrary("pack_test_one"); 
    }

    // 声明一个变量，用于绑定界面上的控件（使用的是 ViewBinding 技术）
    private ActivityMainBinding binding;

    // 【生命周期方法】：**页面被创建时，系统会自动调用这个方法**
    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState); // 必须调用父类的 onCreate

        // 1. **初始化布局绑定对象**（加载页面 XML 文件）
        binding = ActivityMainBinding.inflate(getLayoutInflater());
        
        // 2. 将解析好的界面设置到屏幕上（用户现在能看到 UI 了）
        setContentView(binding.getRoot());
        
        // 3. 打印一行日志。注意这里的 "rea111111111" 是原作者随便写的。
        // 这行代码在实战中很有用：如果是脱壳，看到这行日志打印出来，说明原版代码成功跑起来了。
        Log.i("test", "rea111111111:"+getApplicationContext());
        
        // 4. 获取界面上名叫 sampleText 的 TextView 控件
        TextView tv = binding.sampleText;
        
        // 5.** 调用下面的 native 方法获取一个字符串，并把这个字符串显示在 TextView 控件上**
        tv.setText(stringFromJNI());
    }

    // 【Native 方法声明】：
    // **注意这里的 native 关键字。它表示这个方法在 Java 里没有实现**（没有大括号 {}）。
    // 真正的实现代码在刚才 static 块加载的 C/C++ 库（libpack_test_one.so）里面。
    public native String stringFromJNI();
}
```

> `native`方法：
> 
> 1. 对于开发者：为了安全（或者跑得快），他们喜欢把核心逻辑（比如密码加密、核心算法）写在 C/C\+\+ 里，用 `native` 声明，Java 去调用。
> 
> 2. 对于逆向者：Java 代码很容易被 Jadx 反编译成源码，但 C/C\+\+ 编译出的 `.so` 文件是机器码，极其难懂！高级的壳（比如某某加固的 VMP 壳），核心解密逻辑全在 `.so` 文件里，用 `native` 来掩护自己。
> 
> 

总结一下这个流程：
真正的原版 App 里写了 `native` 方法，壳为了让这个 App 跑起来，必须连带着把原版 App 里的 `.so` 文件也解压、加载出来。

```Python
# 【注意：原脚本这里写漏了参数，应该是 hashlib.sha1(new_dex_data[32:]).digest()】
# 但意思就是重新计算并覆盖。

new_dex_data=new_dex_data[:12]+signature+new_dex_data[32:]

# 更新 Adler-32 校验码（checksum），偏移 8 (0x08)，4字节
# 计算范围是从 signature 开始到文件末尾的所有字节
checksum=zlib.adler32(new_dex_data[12:])
new_dex_data=new_dex_data[:8]+int.to_bytes(checksum,4,'little')+new_dex_data[12:]

# **将刚拼好并修复好的新 Dex 写入到临时文件夹**

src_apk_file.close()
src_dex_file.close()
```

```Java
public final class a {
    
    // 【入口方法】
    public static String a() {
        try {
            // 核心 API：获取当前线程的“方法调用栈”。
            // 简单说：如果方法A调用了B，B调用了C，这行代码能拿到 [A, B, C] 这个调用链。
            // 它返回的是一个数组（StackTraceElement[]）。
            return a(Thread.currentThread().getStackTrace());
        } catch (Exception e) {
            return "none";
        }
    }

    // 【真正干活的私有方法】
    // 参数 stackTraceElementArr 就是上面传过来的调用链数组
    private static String a(StackTraceElement[] stackTraceElementArr) {
        try {
            // 1. 栈深度检查。如果调用链太短（小于等于4），说明不是正常调用，直接返回"none"。
            if (stackTraceElementArr.length <= 4) {
                return "none";
            }
            
            // 2. 取第5个元素（索引为4）。也就是顺着调用链往上数第5层是谁在调用。
            StackTraceElement stackTraceElement = stackTraceElementArr[4];
            
            // 3. 获取这一层的完整类名。例如："com.example.myapp.MainActivity"
            String className = stackTraceElement.getClassName();
            
            // 4. 字符串截取。46是点号'.'的ASCII码。
            // 这一步是为了获取简单类名（比如把 "com.example.MainActivity" 截成 "MainActivity"）
            String substring = className.substring(className.lastIndexOf(46) + 1);
            
            // 5. 再次截取。获取包名（比如把 "com.example.MainActivity" 截成 "com.example"）
            String substring2 = className.substring(0, className.lastIndexOf(46));
            
            // 6. 拼接。把 "包名" + "." + "类名" + ":" + "行号" 拼在一起返回。
            // 拼出来大概长这样："example.MainActivity:42"
            return substring2.substring(substring2.lastIndexOf(46) + 1) + "." + substring + ":" + stackTraceElement.getLineNumber();
        } catch (Exception e) {
            return "none";
        }
    }
}
```

```Java
private static Instruction extractMethod(Dex dex ,RandomAccessFile outRandomAccessFile,ClassDef classDef,ClassData.Method method)
            throws Exception{
        String returnTypeName = dex.typeNames().get(dex.protoIds().get(dex.methodIds().get(method.getMethodIndex()).getProtoIndex()).getReturnTypeIndex());
        String methodName = dex.strings().get(dex.methodIds().get(method.getMethodIndex()).getNameIndex());
        String className = dex.typeNames().get(classDef.getTypeIndex());
        //native函数
        if(method.getCodeOffset() == 0){
            String log = String.format("method code offset is zero,name =  %s.%s , returnType = %s",
                    TypeUtils.getHumanizeTypeName(className),
                    methodName,
                    TypeUtils.getHumanizeTypeName(returnTypeName));
            logger.warn(log);
            return null;
        }
        Instruction instruction = new Instruction();
        //16 = registers_size + ins_size + outs_size + tries_size + debug_info_off + insns_size
        int insnsOffset = method.getCodeOffset() + 16;
        Code code = dex.readCode(method);
        //容错处理
        if(code.getInstructions().length == 0){
            String log = String.format("method has no code,name =  %s.%s , returnType = %s",
                    TypeUtils.getHumanizeTypeName(className),
                    methodName,
                    TypeUtils.getHumanizeTypeName(returnTypeName));
            logger.warn(log);
            return null;
        }
        int insnsCapacity = code.getInstructions().length;
        //insns容量不足以存放return语句，跳过
        byte[] returnByteCodes = getReturnByteCodes(returnTypeName);
        if(insnsCapacity * 2 < returnByteCodes.length){
            logger.warn("The capacity of insns is not enough to store the return statement. {}.{}() -> {} insnsCapacity = {}byte(s),returnByteCodes = {}byte(s)",
                    TypeUtils.getHumanizeTypeName(className),
                    methodName,
                    TypeUtils.getHumanizeTypeName(returnTypeName),
                    insnsCapacity * 2,
                    returnByteCodes.length);

            return null;
        }
        instruction.setOffsetOfDex(insnsOffset);
        //这里的MethodIndex对应method_ids区的索引
        instruction.setMethodIndex(method.getMethodIndex());
        //注意：这里是数组的大小
        instruction.setInstructionDataSize(insnsCapacity * 2);
        byte[] byteCode = new byte[insnsCapacity * 2];
        //写入nop指令
        for (int i = 0; i < insnsCapacity; i++) {
            outRandomAccessFile.seek(insnsOffset + (i * 2));
            byteCode[i * 2] = outRandomAccessFile.readByte();
            byteCode[i * 2 + 1] = outRandomAccessFile.readByte();
            outRandomAccessFile.seek(insnsOffset + (i * 2));
            outRandomAccessFile.writeShort(0);
        }
        instruction.setInstructionsData(byteCode);
        outRandomAccessFile.seek(insnsOffset);
        //写出return语句
        outRandomAccessFile.write(returnByteCodes);

        return instruction;
    }
```

##### mmap

`mmap`（Memory Map，内存映射）最核心的作用是：**向操作系统申请一块内存，并把这块内存和某个文件（比如 DEX 文件）绑定起来。**

> - 当安卓系统加载 DEX 时，它会调用 `mmap`，说：“系统，给我分配一块内存，把磁盘上的 `classes.dex` 映射进去。这块内存我要用来读代码，所以你给我设为‘只读（Read\-Only）’。”
> 
> - 注意：权限（只读/可写）是调用 `mmap` 时顺便传给它的一个参数。系统是按这个参数来分配内存属性的。
> 
> 

Hook mmap函数的目的是在我们**加载dex能够修改dex的属性，****让加载的dex可写****，这样我们才能把字节码填回dex。**

> 如果我们不拦截，这块内存就是只读的。 等壳解密出真实代码想往里写的时候，就会因为“向只读内存写入数据”导致 App 直接崩溃（段错误）。因此，壳必须用一个假函数，去将只刻度权限改为可读可写。
> 
> 

```C++
// 这是一个使用 bhook 框架去拦截系统的代码
bytehook_stub_t stub = bytehook_hook_single(
    getArtLibName(),
    "libc.so",     // 目标：系统的底层库 libc.so
    "mmap",        // 要拦截的函数：mmap
    (void*)**fake_mmap**, // **【核心】把 mmap 的入口，替换成我们自己写的 fake_mmap**
    nullptr,
    nullptr);
if(stub != nullptr){
    DLOGD("mmap hook success!");
}
```

##### LoadMethod

> 这一步是为了在系统真正把某个方法加载进内存准备执行的那一瞬间，把方法的结构和真实代码拿出来。
> 
> 

在Hook LoadMethod函数之前，我们需要了解LoadMethod函数流程。为什么是这个LoadMethod函数，其他函数是否可行？

当一个类被加载的时候，它的调用链是这样的\(部分流程已省略\)：

```Java
ClassLoader.java::loadClass -> DexPathList.java::findClass -> DexFile.java::defineClass -> class_linker.cc::LoadClass -> class_linker.cc::LoadClassMembers -> class_linker.cc::**LoadMethod**
```

也就是说，无论一个类怎么被加载，它都会去调用LoadMethod函数的，我们看一下它的函数原型：

```Java
void ClassLinker::LoadMethod(const **DexFile**& dex_file,
                             const **ClassDataItemIterator**& it,
                             Handle<mirror::Class> klass,
                             ArtMethod* dst);
```

这个函数有两个爆炸性的参数，DexFile和ClassDataItemIterator，我们可以从这个函数得到当前加载函数所在的DexFile结构和当前函数的一些信息，可以看一下`ClassDataItemIterator`结构：

```C++
class ClassDataItemIterator{
  
  ......

  // （把DEX里压缩紧凑的二进制数据，解析成 C++ 能看懂的“方法结构体”）
  struct ClassDataMethod {
    uint32_t method_idx_delta_;  // 方法的索引增量（指向 method_ids 数组中的 MethodId）
    uint32_t access_flags_;      // 方法的访问权限标志（比如 public、static、native 等）
    uint32_t code_off_;          // 代码偏移量（指向这个方法真实字节码在文件里的绝对位置）
    ClassDataMethod() : method_idx_delta_(0), access_flags_(0), **code_off_(0)** {}

   private:
    DISALLOW_COPY_AND_ASSIGN(ClassDataMethod);
  };
  ClassDataMethod method_; // 声明一个结构体实例，用来临时存当前正在读取的方法信息

  // 从 class_data_item 数据流中，读取并解码一个方法的信息，存入上面的 method_ 中
  // （游标往下挪，把下一个方法解包出来）
  void ReadClassDataMethod();

  const DexFile& dex_file_;    // 当前正在扫描的 DEX 文件对象（大户口本）
  size_t pos_;                 // 已经处理过的项数（相当于循环里的 i 计数器）
  const uint8_t* ptr_pos_;     // 指向 class_data_item 二进制数据流的指针（游标卡尺）
  uint32_t last_idx_;          // 上一次读取的字段或方法索引（用于和增量相加，算出当前的绝对索引）
  DISALLOW_IMPLICIT_CONSTRUCTORS(ClassDataItemIterator);
};
```

其中最重要的字段就是`code_off_`。**它的值是当前加载的函数的CodeItem相对于DexFile的偏移，当相应的函数被加载，我们就可以直接访问到它的CodeItem**。其他函数是否也可以？在上面的流程中没有比LoadMethod更适合我们Hook的函数，所以它是最佳的Hook点。



Hook LoadMethod稍微复杂一些，倒不是Hook代码复杂，而是Hook触发后处理的代码比较复杂，我们要适配多个Android版本，每个版本LoadMethod函数的参数都可能有改变，幸运的是，LoadMethod改动也不是很大。

那么，我们如何读取ClassDataItemIterator类中的`code_off_`呢？比较直接的做法是计算偏移，然后在代码中维护一份偏移。不过这样的做法不易阅读很容易出错。dpt的做法是把`ClassDataItemIterator`类拷过来，然后将ClassDataItemIterator引用直接转换为我们自定义的`ClassDataItemIterator`引用，这样就可以方便的读取字段的值。

> 在 DEX 文件里，每个方法的真实代码都存放在一个叫 `CodeItem` 的结构里。这个结构里有一个极其关键的数组，就叫 `insns` 数组，里面装的是真正的机器字节码。
> 
> 

> - 在脱壳工具的 C\+\+ 源码中，**完全参照对应 Android 版本的 AOSP 源码，定义一个与系统完全一致的 ****`ClassDataItemIterator`**** 结构体。**
> 
> - 在 Hook 拦截到数据时，获取系统传入的对象指针，**将其强制类型转换（Cast）为自定义的结构体指针。**
> 
> - 利用 C\+\+ 编译器根据自定义结构体**自动计算偏移量**的特性，直接通过 `it->method_.code_off_` 安全地读取数据。
> 
> 

下面是LoadMethod被调用后做的操作，逻辑是读取存在map中的insns，然后将它们填回指定位置。

```C++
void LoadMethod(void *thiz, void *self, const void *dex_file, const void *it, const void *method,
                void *klass, void *dst) {

    if (g_originLoadMethod25 != nullptr
        || g_originLoadMethod28 != nullptr
        || g_originLoadMethod29 != nullptr) {
        uint32_t location_offset = getDexFileLocationOffset();
        uint32_t begin_offset = getDataItemCodeItemOffset();
        callOriginLoadMethod(thiz, self, dex_file, it, method, klass, dst);

        ClassDataItemReader *classDataItemReader = getClassDataItemReader(it,method);


        uint8_t **begin_ptr = (uint8_t **) ((uint8_t *) dex_file + begin_offset);
        uint8_t *begin = *begin_ptr;
        // vtable(4|8) + prev_fields_size
        std::string *location = (reinterpret_cast<std::string *>((uint8_t *) dex_file +
                                                                 location_offset));
        if (location->find("base.apk") != std::string::npos) {

            //code_item_offset == 0说明是native方法或者没有代码
            if (classDataItemReader->GetMethodCodeItemOffset() == 0) {
                DLOGW("native method? = %s code_item_offset = 0x%x",
                      classDataItemReader->MemberIsNative() ? "true" : "false",
                      classDataItemReader->GetMethodCodeItemOffset());
                return;
            }

            uint16_t firstDvmCode = *((uint16_t*)(begin + classDataItemReader->GetMethodCodeItemOffset() + 16));
            if(firstDvmCode != 0x0012 && firstDvmCode != 0x0016 && firstDvmCode != 0x000e){
                NLOG("this method has code no need to patch");
                return;
            }

            uint32_t dexSize = *((uint32_t*)(begin + 0x20));

            int dexIndex = dexNumber(location);
            auto dexIt = dexMap.find(dexIndex - 1);
            if (dexIt != dexMap.end()) {

                auto dexMemIt = dexMemMap.find(dexIndex);
                if(dexMemIt == dexMemMap.end()){
                    changeDexProtect(begin,location->c_str(),dexSize,dexIndex);
                }


                auto codeItemMap = dexIt->second;
                int methodIdx = classDataItemReader->GetMemberIndex();
                auto codeItemIt = codeItemMap->find(methodIdx);

                if (codeItemIt != codeItemMap->end()) {
                    CodeItem* codeItem = codeItemIt->second;
                    uint8_t  *realCodeItemPtr = (uint8_t*)(begin +
                                                classDataItemReader->GetMethodCodeItemOffset() +
                                                16);

                    memcpy(realCodeItemPtr,codeItem->getInsns(),codeItem->getInsnsSize());
                }
            }
        }
    }
}
```

### 二代脱壳

操作步骤总结回忆：

**一、 Java 层：实施主动调用与触发**

此阶段基于 Frida 脚本，**通过反射机制遍历并强制加载目标类，从而触发壳的解密流程**。

1. 枚举 ClassLoader：调用 `Java.enumerateClassLoaders` 遍历当前进程内的所有类加载器，以定位包含目标代码的 `BaseDexClassLoader` 实例。

2. 遍历 dexElements：通过反射获取 `BaseDexClassLoader` 内部的 `pathList` 属性，进而获取其持有的 `dexElements` 数组。该数组包含了当前内存中已加载的所有 DEX 文件（`DexFile` 对象）。

3. 获取类清单：遍历 `dexElements` 中的每一个 `DexFile`，调用 `dexFile.entries()` 方法，获取该 DEX 文件中定义的所有类的全限定名列表。

4. 强制加载触发（核心）：遍历获取到的类名，调用 `classLoader.loadClass(className)`。此操作**强制向系统请求加载这些类**。如果该类属于被抽取的类，必将触发壳底层的解密与回填逻辑。

**二、 Native 层：壳的解密与内存回填**

当 Java 层发起 `loadClass` 请求后，系统底层（ART 虚拟机）会执行类加载流程。二代壳通常会在 Native 层对相关执行函数（如 `LoadMethod` 或解释器入口）进行 Hook。

1. 拦截执行流：**当系统尝试加载类或执行方法时，壳的 Hook 代码接管执行流。**

2. 内存权限修改：由于系统默认以只读（Read\-Only）方式 `mmap` 映射 DEX 文件，壳需先通过 Hook `mmap` 或调用 `mprotect`，将目标内存区域的权限修改为可读写（Read\-Write）。

3. 解密与回填（CodeItem 修复）：壳从自身的加密数据段（或外部文件）中读取被抽取的真实字节码，完成解密后，通过 `memcpy` 将真实的指令数据（`insns`）覆写回 DEX 内存中对应方法的 `CodeItem` 区域。

## 三代壳\-\-VMP

感觉各大文章基本都在进行实操（？

[Learning\-with\-Claude/security/android\_reversing/28\-packers\-overview\.md at main · yPin9/Learning\-with](https://github.com/yPin9/Learning-with-Claude/blob/main/security/android_reversing/28-packers-overview.md)



三代壳的核心标志是 VMP（Virtual Machine Protection，虚拟机保护）。

与二代壳的对比：

- 二代抽取壳（Code Item 抽取）：壳把原生的 Dalvik 字节码抽走加密。运行时，壳解密出原本的字节码，填回 `CodeItem`，让 Android 系统的 ART 虚拟机去执行。脱壳工具在回填点蹲守，就能截获原生的指令。

- 三代 VMP 壳（指令虚拟化）：壳根本不把原生代码填回 DEX 中。**壳在加固时，将原生的 Dalvik 字节码转换成了自定义的指令集（自定义 OpCode）**。运行时，壳不依赖系统的 ART 虚拟机，而是使用自己用 C/C\+\+ 编写的解释器（VM Engine）逐条解释执行这些自定义指令。



> 首先我们应该先了解一下Dalvik字节码
> 
> Dalvik 字节码是安卓系统独有的一种中间语言（Intermediate Language）
> 
> 我们用正常的编译流程来看：
> 
> 1. 人类写代码：Java / Kotlin 源码（人能看懂）。
> 
> 2. 第一次翻译（编译）：编译器（如 `d8`）把源码翻译成 Dalvik 字节码（存在 `.dex` 文件里）。注意：这时候手机 CPU 依然看不懂它。
> 
> 3. 第二次翻译（运行）：安卓系统里的 ART 虚拟机（一个用 C\+\+ 写的软件），把 Dalvik 字节码一句句翻译成真正的 ARM 机器码（CPU 能懂的 0 和 1）。
> 
> 所以，Dalvik 字节码是写给“安卓虚拟机”看的指令集，而不是写给真实 CPU 看的。
> 
> 



VMP 为何最难？

无论第一代/第二代外壳如何隐藏，明文的 Dalvik 字节码总会在某一时刻出现在内存中（脱壳就在那一瞬间）。而 VMP 的关键在于让明文的 Dalvik 字节码永远不会出现——内存中只有私有的 VM 指令以及 VM 解释器。**你所能获取的只是 VM 字节码，而非 Dalvik 字节码**，因此之前提到的那些基于魔法数值扫描及转储的方法完全无效。

对付 VMP 只能逆那台 VM：逆出 VM 解释器的 dispatch 迴圈（分发循环）、还原每条私有指令对应的 Dalvik 语义（去虚拟化），把 VM 字节码翻译回 Dalvik。工程量巨大，是加固对抗的天花板。好消息是 VMP 核心存在性能代价（VM 解释比原生代码慢），厂商通常只对最关键的几个方法应用 VMP，其余则使用第二代内核——因此你大多只需对少数几个核心方法进行去虚拟化处理即可。
