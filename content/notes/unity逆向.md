## 前置基础

- C 语言：就像是用砖块和水泥直接盖房子。盖出来的房子（程序）极其坚固，但只有懂汇编的人才能看懂它的结构。这就是C 逆向（用 IDA 硬啃汇编）。

- C\# 语言：这是一种更高级的语言，就像是用预制板盖房子。C\# 代码编译后，不是机器码，而是一种叫** IL（中间语言）** 的东西。

- \.NET：就是能让预制板（C\# 编译的 IL）顺利组装起来的脚手架和运行环境。微软搞出 \.NET，就是为了让 C\# 跑起来。**C\# 运行在 \.NET 上。**

- Unity：这是一个非常流行的游戏引擎（游戏生产车间）。很多游戏都是用 Unity 开发的。Unity 默认就是用 C\# 来写游戏逻辑的。

### `.NET`编译

\.NET主要包含：

1. `C#` 语言：写代码用的语言，本质上是给 \.NET 量身定做的语法。但 \.NET 不仅支持 C\#，还支持 [VB\.NET](https://vb.net/)、F\# 等。

2. IL（中间语言）与元数据：编译器（比如 Roslyn）把 C\# 编译成的东西。它不是机器码，而是 \.NET 平台能看懂的“通用图纸”。

3. CLR（公共语言运行时）/ Mono：真正负责**执行 **`IL` 的“引擎”。它**负责把 **`IL`** 翻译成机器码**，还负责内存管理（垃圾回收 GC）、安全校验。

`.NET`编译可以是JIT和AOT两种类型

#### JIT

Just in time 即时编译

即：**程序运行的时候，才开始一行一行（或一段一段）地把代码翻译成机器码。**

- **特点：**

    - **产物：** 中间语言（`IL`）。这是一种“半成品”，它保留了极其丰富的原书信息（类名、变量名、结构）。

    - **跨平台：**能在`linux`和`windows`上跑

    - **逆向难度低：** 因为 IL 保留了太多信息，dnSpy 这种工具可以直接把 IL “逆向翻译”回源代码，几乎一模一样。

- **典型代表：** 标准的 C\#, Java, Python \(PyPy\), JavaScript \(V8\)。

- **工具：** **dnSpy**, ILSpy \(用来读 IL\)。

#### AOT

Ahead of time 提前编译

即：**在程序运行之前，开发者就已经把代码翻译成了机器能懂的“最终指令”。**

- **特点：**

    - **产物：** 纯粹的机器码（01010…），对应 x86/x64 汇编指令。

    - **启动快：** 因为已经翻译好了，打开就能跑。

    - **逆向难度大：** 就像你拿到了翻译好的中文书，原文的“句式结构”、“独特的修辞”（即类名、函数名、元数据）很多都丢了。你只能看到最终意思。

- **典型代表：** C, C\+\+, Rust, Go, **C\# Native AOT**。

- **工具：** **IDA**, Ghidra \(用来读汇编\)。



### mono与IL2CPP

unity逆向采用了 **C 逆向**和 **`.NET`** 逆向**两套底层技术，需要我们根据情况选择不同的工具。

（unity提供了两种将`C#`代码变成机器看懂的语言的方式（打包方式）

1. **Mono 方式**：**直接带着 \.NET 的运行环境**。C\# 编译成 IL，游戏运行时由 Mono 来解释执行。这时，Unity 逆向 = \.NET/C\# 逆向。

> Mono:一个由 Xamarin公司主持的自由开放源代码项目，目标是创建一系列符合ECMA标准（Ecma\- 334和Ecma\-335）的\.NET工具包括C\#编译器和通用语言架构。与微软的\.NET Framework（共通语言运行平台）不同Mono项目不仅可以运行于Windows系统上，还可以运行于 Linux，FreeBSD，Unix，OS X和Solaris，甚至一些游戏平台。**Mono使得**`C#`**这门语言有了很好的跨平台能力。**
> 
> 

2. **IL2CPP 方式**：把 C\# 代码先转成 C\+\+ 代码，再编译成原生机器码（就是 C 逆向的东西）。这时，Unity 逆向 = C 逆向 \+ 元数据解析。

## 正文

在市面上普遍有两种unity逆向，他们分别使用不同的编译方式，解决的思路也不同

### Mono编译

这是原始的编译方式，也是最容易攻破，不太安全的一种编译方式，生成的游戏文件夹中，游戏的关键代码文件会直接生成在` _Data\Managed\Assembly-CSharp.dll`的文件之中，出题人一般会想让我们通过破解游戏逻辑，或者在`c#`中进行解密来获取到最后的flag。

> 算是对上述概念的一个小总结：
> 
> Unity3D 最大的一个特点是一次制作，多平台部署，而这一核心功能是 Mono 实现的。可以说一直以来 Mono 是 Unity3D 核心中的核心，是 Unity3D 跨平台的根本。Mono 是一个开源的 \.NET 框架实现，它允许 Unity 在多种平台上运行，特别是在支持 \.NET 的平台上，Mono 提供了兼容的运行时和类库。然而，Mono 并不是完全安全的，它会将源代码编译成 IL（中间语言）代码，这使得逆向工程变得相对容易。为了增强安全性，Unity 从 2014 年开始引入 IL2CPP（Intermediate Language to C\+\+），这一技术将中间语言（IL）代码转化为 C\+\+ 代码，然后再编译成机器码，从而提高了代码的安全性和性能。不过目前仍然有大量的 Unity 游戏使用 Mono 打包方式，所以掌握 Mono 逆向技术仍然非常重要。
> 
> 

#### 文件结构区分

Mono 打包方式逆向比较简单，其**核心代码都在 **`game/assets/bin/data/Managed/Assembly-CSharp.dll`** 这个 dll 文件中**，使用 dnSpy 进行分析，几乎就是可以明文随便篡改。

当我们拿到一个 Unity 游戏时，首先要判断它是 Mono 打包还是 IL2CPP 打包，判断方法很简单：如果在游戏目录下的 **`Data/Managed`** 文件夹中能找到 **`Assembly-CSharp.dll`** 文件，那就是 Mono 打包；如果在游戏目录下能找到一个很大的 **`GameAssembly.dll`** 文件以及 **`Data/il2cpp_data`** 文件夹，那就是 IL2CPP 打包。**

![](/images/unity逆向/image%202.png)



Mono 打包的游戏文件结构通常如下：游戏根目录下有一个 `Data` 文件夹，里面包含了游戏的所有资源和代码。`Data/Managed` 文件夹中存放着所有的 dll 文件，其中 `Assembly-CSharp.dll` 是游戏的主要逻辑代码，`Assembly-CSharp-firstpass.dll` 是一些第三方插件的代码，其他的 dll 文件则是 Unity 引擎和 \.NET 框架的库文件。我们**逆向的重点就是 **`Assembly-CSharp.dll`** 这个文件，因为游戏的核心逻辑都在这里面。**

#### dnSpy分析Mono游戏

使用 dnSpy 打开 `Assembly-CSharp.dll` 文件，可以看到游戏的所有类和方法。Unity 游戏通常会有一些特殊的类，比如继承自 `MonoBehaviour` 的类，这些类是 Unity 的脚本组件，会被挂载到游戏对象上。`MonoBehaviour` 类有一些特殊的方法，比如 `Start` 方法会在脚本启动时调用一次，`Update` 方法会在每一帧调用一次，`OnClick` 方法会在按钮被点击时调用。在逆向 Unity 游戏时，我们通常会重点关注这些方法，因为游戏的主要逻辑往往就在这些方法中。



另外，Unity 游戏中经常会使用一些特殊的类和方法，比如 `PlayerPrefs` 类用于存储游戏数据，`SceneManager` 类用于场景管理，`Input` 类用于处理输入，`Debug.Log` 方法用于输出调试信息。熟悉这些常用的 Unity API 能帮助我们更快地理解游戏的逻辑。在 dnSpy 中，我们可以使用搜索功能快速定位关键代码，比如搜索 "flag"、"password"、"check" 等关键词，往往能找到验证逻辑所在的位置。

#### Mono游戏常见保护和绕过

虽然 Mono 打包的游戏逆向起来比较简单，但是开发者也会采取一些保护措施来增加逆向的难度。常见的保护措施包括**代码混淆、字符串加密、反调试、完整性校验**等。代码混淆是最常见的保护措施，通过将类名、方法名、变量名替换为无意义的字符串来增加阅读难度，我们可以使用 `de4dot` 等工具来去除混淆。字符串加密是将程序中的字符串常量加密存储，在运行时再解密使用，这样可以防止我们通过搜索字符串来定位关键代码，对于这种保护我们可以通过**动态调试**或者**分析解密函数**来获取原始字符串。



反调试是检测程序是否在调试器中运行，如果检测到调试器则退出或者改变程序行为，常见的反调试方法包括**检测调试器进程、检测调试标志、时间检测**等，我们可以通过**修改检测代码**或者**使用反反调试插件**来绕过。完整性校验是计算程序文件的哈希值，在运行时检查文件是否被修改，如果检测到修改则退出程序，对于这种保护我们可以**找到校验代码并将其 nop 掉或者修改校验逻辑**。总的来说，Mono 游戏的保护措施相对容易绕过，因为我们可以直接修改 IL 代码，而且 dnSpy 提供了强大的编辑和调试功能。

### IL2CPP

#### 技术原理

**IL2CPP 的工作原理是将 C\# 代码编译成 IL 中间语言后，再通过 IL2CPP 工具将 IL 代码转换为 C\+\+ 代码，最后使用平台对应的 C\+\+ 编译器将 C\+\+ 代码编译成机器码。**这个过程相比 Mono 的 JIT（Just\-In\-Time）编译方式有几个明显的优势：首先是性能提升，因为代码是提前编译成机器码的，运行时不需要 JIT 编译，所以执行效率更高；其次是安全性提升，因为代码已经被编译成机器码，逆向难度大大增加，不像 Mono 那样可以直接反编译成源码；最后是平台兼容性更好，因为 IL2CPP 可以将代码编译成各个平台的原生代码，不需要依赖 Mono 运行时。

![](/images/unity逆向/image%205.png)

从逆向的角度来看，IL2CPP 打包的游戏主要有两个特征文件：一个是 **`GameAssembly.dll`**（Windows 平台）或 **`libil2cpp.so`**（Android/Linux 平台），这个文件包含了游戏的所有机器码，体积通常比较大；另一个是 **`global-metadata.dat`** 文件，位于 **`Data/il2cpp_data/Metadata`** 目录下，这个文件包含了**游戏的元数据信息，包括类名、方法名、字符串常量等**。虽然代码已经被编译成机器码，但是 Unity 为了支持反射等功能，必须保留这些元数据信息，这就给我们的逆向分析提供了突破口。

#### IL2CPP游戏的识别

判断一个 Unity 游戏是否使用 IL2CPP 打包非常简单，只需要查看游戏目录的文件结构即可。如果在游戏根目录下能找到一个很大的 `GameAssembly.dll` 文件（Windows 平台），并且在 `Data` 目录下有一个 `il2cpp_data` 文件夹，那就是 IL2CPP 打包。具体来说，`il2cpp_data` 文件夹中会有一个 `Metadata` 子文件夹，里面包含 `global-metadata.dat` 文件，这个文件存储了游戏的全局元数据。

#### Il2CppDumper 工具详解

Il2CppDumper 是一个开源的 IL2CPP 逆向工具，

项目地址是 [https://github\.com/Perfare/Il2CppDumper](https://github.com/Perfare/Il2CppDumper) 。

这个工具可以**从 **`GameAssembly.dll`** 和 **`global-metadata.dat`** 文件中提取出游戏的**符号信息**，包括类名、方法名、字段名、字符串常量等，然后生成可以导入 IDA、Ghidra 等反汇编工具的脚本文件。**Il2CppDumper 的工作原理是解析 `global-metadata.dat` 文件获取元数据信息，然后分析 `GameAssembly.dll` 文件找到对应的函数地址，最后将元数据和地址信息关联起来生成输出文件。这个工具是 IL2CPP 逆向的必备工具，几乎所有的 IL2CPP 逆向工作都需要先使用 Il2CppDumper 提取符号信息。

![](/images/unity逆向/image%203.png)

Il2CppDumper 的使用非常简单，直接运行 `Il2CppDumper.exe` 并依次选择 IL2CPP 的可执行文件（`GameAssembly.dll`）和 `global-metadata.dat` 文件，然后根据提示输入相应信息即可。程序会首先提示选择模式，通常有自动模式（Auto）、手动模式（Manual）和自动加强模式（Auto\(Advanced\)）等选项。自动模式会尝试自动识别平台和架构，适用于大多数情况；手动模式需要用户手动选择平台、架构、Unity 版本等信息，适用于自动识别失败的情况；自动加强模式会使用更复杂的算法来识别，但可能需要更长的时间。对于常见的 Windows x64 游戏，选择自动模式即可。

##### 输出文件

程序运行完成后将在当前运行目录下生成输出文件，主要包括以下几个部分：



**DummyDll 文件夹**：包含所有还原的 DLL 文件，可以使用 dnSpy、ILSpy 或者其他 \.NET 反编译工具查看具体信息。这些 dll 文件虽然不能直接运行（因为方法体是空的，只有方法签名），但是可以让我们了解游戏的类结构和方法签名，这对于理解程序逻辑非常重要。DummyDll 中的 dll 文件保留了原始的命名空间、类名、方法名、字段名、属性名等信息，以及方法的参数类型和返回值类型。通过查看这些信息，我们可以快速了解游戏的架构，比如有哪些主要的类、每个类负责什么功能、类之间的继承关系等。这些 dll 文件还可以用于提取 Unity 的 `MonoBehaviour` 和 `MonoScript`，适用于 UtinyRipper 或者 UABE 等资源提取工具。



**dump\.cs 文件**：**存放了可执行程序的 dump 信息，包含了所有类和方法的定义**。这个文件是一个纯文本文件，包含了游戏中所有类的完整定义，包括类的继承关系、字段、属性、方法、事件等。虽然方法体是空的，但是方法签名是完整的，包括参数名、参数类型、返回值类型等。这个文件可以用于快速浏览游戏的代码结构，比如搜索某个关键词（如 "encrypt"、"decrypt"、"flag" 等）来找到相关的类和方法。由于是纯文本文件，可以使用任何文本编辑器打开，也可以使用 grep、findstr 等命令行工具进行搜索。



**script\.json 文件**：**用于 IDA 和 Ghidra 脚本，包含了所有函数的地址和名称的映射关系**。这个文件是 JSON 格式的，包含了每个方法的地址（相对于模块基址的偏移）、名称（类名和方法名的组合）、参数信息等。IDA 和 Ghidra 的脚本会读取这个文件，然后在反汇编工具中为每个函数重命名，使得函数名从无意义的地址变成有意义的类名和方法名。这大大提高了静态分析的效率，因为我们可以直接通过函数名了解函数的功能，而不需要逐个分析汇编代码。



**il2cpp\.h 文件**：**包含结构体的头文件，可以在 IDA 中导入这些结构体定义**。这个文件定义了 IL2CPP 运行时使用的各种数据结构，比如 `Il2CppObject`、`Il2CppString`、`Il2CppArray`、`Il2CppClass`、`MethodInfo` 等。在 IDA 中导入这个头文件后，IDA 可以自动识别这些结构体，使得反编译代码更加易读。比如，当我们看到一个指针被当作 `Il2CppString*` 使用时，IDA 会自动显示字符串的长度和内容，而不是显示为一个无意义的地址。



**stringliteral\.json 文件**：**包含所有字符串常量的信息，存放了地址和字符串的对应关系。**这个文件是 JSON 格式的，包含了游戏中所有的字符串常量，以及它们在内存中的地址。通过这个文件，我们可以快速找到某个字符串的位置，然后在 IDA 中查找引用该字符串的函数。这对于定位关键代码非常有用，比如我们可以搜索 "password"、"key"、"flag" 等关键词，找到相关的字符串，然后定位到使用这些字符串的函数。



**ida\.py / ida\_with\_struct\.py**：用于 IDA 的脚本文件。`ida.py` 是基本版本，只会为函数重命名；`ida_with_struct.py` 是增强版本，除了重命名函数外，还会读取 `il2cpp.h` 文件并在 IDA 中应用结构信息。使用增强版本可以获得更好的反编译效果，但可能需要更长的加载时间。



**ghidra\.py / ghidra\_wasm\.py**：用于 Ghidra 的脚本文件。`ghidra.py` 用于普通的 IL2CPP 程序，`ghidra_wasm.py` 用于 WebAssembly 格式的 IL2CPP 程序（主要用于 Web 平台的 Unity 游戏）。



#### IDA分析IL2CPP代码

使用 Il2CppDumper 提取出符号信息后，我们就可以使用 IDA 来分析 `GameAssembly.dll` 了。首先用 IDA 打开 `GameAssembly.dll` 文件，等待 IDA 自动分析完成。然后**通过 IDA 的脚本功能加载 Il2CppDumper 生成的符号信息**，具体操作是：点击 `File -> Script file`，选择 Il2CppDumper 输出目录中的 `ida.py` 脚本（如果需要结构体信息可以选择 `ida_with_struct.py`），运行脚本后会提示选择 `script.json` 文件，选择后脚本会自动为所有函数重命名并添加注释。如果使用 `ida_with_struct.py`，还会提示选择 `il2cpp.h` 文件，这个文件包含了 IL2CPP 运行时的结构体定义，导入后可以让 IDA 更好地识别数据结构。



加载脚本后，**IDA 中的函数名就会从无意义的地址变成有意义的类名和方法名**，比如 `PlayerController_Update` 表示 `PlayerController` 类的 `Update` 方法，`hOOK_SYC` 表示 `hOOK` 类的 `SYC` 方法。这样我们就可以像分析普通的 C/C\+\+ 程序一样分析 IL2CPP 代码了，虽然代码已经被编译成机器码，但是有了符号信息后分析起来就容易多了。另外，我们还可以通过导入 `il2cpp.h` 文件来使用结构体定义，这样在分析涉及到 Unity 内部结构的代码时会更加方便，比如 `Il2CppString`、`Il2CppArray` 等结构体。



在分析 IL2CPP 代码时，有几个技巧可以帮助我们快速定位关键代码：首先是**搜索字符串**，虽然字符串已经被编译到代码中，但是我们可以通过 `stringliteral.json` 文件找到字符串的地址，然后在 IDA 中查找引用这个地址的函数；其次是**搜索类名和方法名**，通过 Il2CppDumper 恢复的符号信息，我们可以直接在 IDA 的函数列表中搜索感兴趣的类和方法，比如搜索 "flag"、"encrypt"、"decrypt" 等关键词；最后是**分析 **`DummyDll`** 中的 dll 文件**，虽然这些 dll 不能运行，但是可以让我们了解类的结构和方法的参数类型，这对于理解 IDA 中的汇编代码很有帮助，特别是当函数参数较多或者涉及复杂数据结构时。

#### CE 工具在 IL2CPP 逆向中的应用

下载：`https://www.cheatengine.org/downloads.php`

虽然 IL2CPP 将代码编译成了机器码，但是 CE（Cheat Engine）工具仍然可以用于动态分析 IL2CPP 游戏。CE 是一个功能强大的**内存编辑和调试**工具，最初是为游戏修改而设计的，但在逆向工程中也有广泛的应用。CE 的 Mono 功能虽然**主要针对 Mono 游戏，可以直接查看和修改 Mono 对象、调用 Mono 方法，但是对于 IL2CPP 游戏，我们仍然可以使用 CE 的内存搜索和修改功能**。通过 CE 附加到游戏进程，我们可以**搜索和修改游戏中的变量值，比如金币数量、血量、经验值、物品数量等**。虽然我们看不到像 Mono 游戏那样清晰的类结构和对象层次，但是通过内存搜索仍然可以找到关键数据的位置。

![](/images/unity逆向/QQ_1792037828130.png)

CE 的**内存搜索**功能非常强大，支持多种数据类型（整数、浮点数、字符串、字节数组等）和搜索方式（精确值、未知初始值、增加了、减少了等）。对于 IL2CPP 游戏，最常用的搜索方式是精确值搜索和变化值搜索。精确值搜索适用于我们知道变量当前值的情况，**比如游戏界面显示金币数量为 100，我们就可以搜索值为 100 的内存地址。**变化值搜索适用于我们不知道变量具体值但知道变化规律的情况，比如我们知道某个操作会使某个值增加，就可以使用"增加了"搜索来筛选地址。通过多次搜索和筛选，我们通常可以将候选地址缩小到几个甚至一个，然后就可以修改这个地址的值来改变游戏行为。

另外，CE 还有一个非常有用的功能是 "Find out what accesses this address"（**找出访问这个地址的代码**）和 "Find out what writes to this address"（**找出写入这个地址的代码**）。通过这两个功能，我们可以**找到修改某个变量的代码位置，然后在 IDA 中定位到对应的函数进行分析**。具体操作是：右键点击地址列表中的地址，选择相应的功能，然后在游戏中触发修改该变量的操作，CE 会记录下所有访问或写入该地址的指令。这些指令会显示为汇编代码，包括指令地址、操作码、操作数等信息。我们可以**双击某条指令，CE 会打开内存查看器并定位到该指令的位置，显示周围的汇编代码**。记下指令的地址后，我们可以在 IDA 中跳转到这个地址（按 G 键输入地址），查看对应的函数和反编译代码。这种动静结合的分析方法在 IL2CPP 逆向中非常有效，特别是当静态分析遇到困难时，可以通过动态分析来突破。

###### 与010editor的区别

010 Editor 的核心功能是“**看底层字节**”。

> 如果游戏直接把字符串 `NSSCTF{you_know_` 写在文件里（哪怕混在二进制中），010 Editor 的查找功能就能直接在底层字节（`4E 53 53...`）中匹配到它。这是最快、最暴力的方法。
> 
> 

> 如果你用 010 Editor 打开一个游戏的图片文件，你只能看到一大堆十六进制的像素点，你没法把它变成一张能看的 PNG 图片；如果你看到一段被加密过的乱码，010 Editor 也只能干瞪眼，没法还原逻辑。
> 
> 

当“明文直接写死”这个前提不成立时，就必须要用到 AssetRipper 

场景 1：图片/音频隐写（最常见）
如果 **Flag 是一张二维码、一张带有 LSB 隐写的图片，或者一段频谱图里有文字的音频**。你用 010 Editor 打开，只能看到一堆乱码。
AssetRipper 的作用：它能把这些二进制数据解析出来，还原成标准的 `.png` 和 `.wav` 文件。你才能拿去用 Stegsolve 或者 Audacity 做 Misc 分析。

场景 2：文本被加密或压缩（TextAsset）
如果开发者把 Flag 存成 `.txt` 放进了游戏里，但用 Base64 或者异或加密了。
010 Editor：只能搜到 `S0Z...`（Base64乱码），搜不到 `NSSCTF`。
AssetRipper：它知道 Unity 的打包格式，能帮你**把资源提取出来，有时甚至能自动帮你解码**。

场景 3：需要**看对象之间的“依赖关系”**（追踪逻辑）
你之前用 010 Editor 搜到了 `NSSCTF{you_know_`，但你知道这串文字是挂在哪个 UI 上的吗？如果逻辑更复杂，需要找“谁调用了这个变量”怎么办？
AssetRipper 导出的 `level0.unity` 是带有层级结构的 YAML 文本。你能清晰地看到：`GameObject (名字叫FlagText) -> 挂载了 Text 组件 -> 里面填了这串文字`。这是 010 Editor 这种纯字节搜索完全做不到的。

场景 4：遇到** IL2CPP 打包的游戏**
这次遇到的是 Mono 模式（有 `Assembly-CSharp.dll`）。如果下次遇到 IL2CPP 模式，打开 `Data` 文件夹，里面是没有 DLL 的，只有 `GameAssembly.dll` 和 `global-metadata.dat`。dnSpy 直接失效！
这时候，我们只能先用 AssetRipper 把资源拆出来找图片和文本，再用 `Il2CppDumper` 去逆向代码逻辑。

场景 5：提取模型、材质，或者需要**修补/替换游戏资源**

如果你想把游戏里的玩家模型换成别的，或者把游戏里的提示音换成你自己的，你必须用 AssetRipper 导出整个 Unity 工程，然后在 Unity 编辑器里替换。

首先我们需要找到扣血代码

![](/images/unity逆向/QQ_1792143948715.png)

- 此时 `RBX = 02AF5190`，这是敌方 HAL 的“对象基址”。

- `[rbx+08]` 就是当前血量。我们选中的地址 `02AF5198` 正好就是 `RBX+08`。此时血量是 498（因为攻击了一次）。

- 这条指令的意思是：把计算后的新血量（存在 `xmm0` 里）写入到这个敌人的内存里。

而当我们寻找自己血量地址的时候会发现

![](/images/unity逆向/QQ_1792144603764.png)

- 当敌人掉血时，`RBX = 02AF5190`，扣血代码是 `movss [rbx+08], xmm0`。

- 当我们自己掉血时，`RBX = 02AB5180`，扣血代码依然是 `movss [rbx+08], xmm0`。

因此这就是教程说的共享代码 我们不能通过修改这个来完成这个题目的要求

因此这道题的关键点是**找出能够识别敌我代码的地方**

###### 内存区域

我们浏览一下敌人和我们的内存区域

![](/images/unity逆向/QQ_1792145042488.png)

![](/images/unity逆向/QQ_1792145080857.png)

分析结果：

敌方 HAL 的结构体（基址 `02AF5190`）：

- `02AF5198`（偏移 `+08`）：`00 00 F9 43` \-\> 这是单浮点数 498\.0（当前血量）。

- `02AF51A4`（偏移 `+14`）：`02 00 00 00` \-\> 这是整数 2（敌人阵营ID）。

- `02AF51A8`（偏移 `+18`）：`03 48 41 4C` \-\> 这是字符串 `HAL`。

我方 Dave 的结构体（基址 `02AB5180`）：

- `02AB5188`（偏移 `+08`）：`00 00 BA 42` \-\> 这是单浮点数 93\.0（当前血量）。

- `02AB5194`（偏移 `+14`）：`01 00 00 00` \-\> 这是整数 1（玩家阵营ID）。

- `02AB5198`（偏移 `+18`）：`04 44 61 76 65` \-\> 这是字符串 `Dave`。

扣血代码 `movss [rbx+08], xmm0` 既扣敌人的血，也扣我们的血。
但敌人的 `[rbx+14]` 是 2，我们的 `[rbx+14]` 是 1。
所以，**只要判断 **`[rbx+14]`** 是不是 2，就能完美区分敌我！**

我们回到CE反汇编窗口，然后对血量进行代码注入

![](/images/unity逆向/QQ_1792146189670.png)

原代码为：

```Assembly language
alloc(newmem,2048,"Tutorial-x86_64.exe"+499ED) 
label(returnhere)
label(originalcode)
label(exit)

newmem: //this is allocated memory, you have read,write,execute access
//place your code here

originalcode:
movss [rbx+08],xmm0

exit:
jmp returnhere

"Tutorial-x86_64.exe"+499ED:
jmp newmem
returnhere:

```

我们将代码改为：

```Assembly language
alloc(newmem,2048,"Tutorial-x86_64.exe"+499ED) 
label(returnhere)
label(originalcode)
label(exit)

newmem:
  // 1. 读取当前单位的最大血量（+04），并与 500.0 比较
  movss xmm1, [rbx+04]       // 将最大血量读入 xmm1
  comiss xmm1, [hp_500]      // 比较 xmm1 和 500.0
  jne skip_damage            // 如果不等于 500.0（说明是自己人，100血），跳到 skip_damage 跳过扣血

  // 2. 是敌人，照常执行扣血代码
  movss [rbx+08], xmm0
  jmp exit

skip_damage:
  // 3. 是自己人，直接跳走（无敌！）
  jmp exit

originalcode:
  nop
  nop
  nop
  nop
  nop

exit:
  jmp returnhere

// 定义常量 500.0
hp_500:
  dd 500.0

"Tutorial-x86_64.exe"+499ED:
  jmp newmem
returnhere:

```

一开始代码改的有点问题所以这个教程崩了（

但是这个代码注入应该没啥问题 因为刚刚出现了访问冲突

> 刚刚加的错误指令是：
> 
> `cmp dword ptr [rbx+14], 2`，意思是：去 `rbx` 大楼的 `+14` 房间看看阵营是不是敌人。
> 
> **为什么会崩？**
> 因为在游戏运行过程中，寄存器 `rbx` 并不总是指向一个完整的“单位结构体”。有时候（比如刚开局、单位死亡、或者调用了其他组件时），`rbx` 可能只是一个很小的子对象（比如只有 `+00` 到 `+0C` 这几个房间）。当你强行去推开 `+14` 房间的门时，发现那里根本就是一堵墙（越界了），游戏引擎为了自保，立刻切断了进程，弹出了这个报错。
> 
> 但是这个代码中
> 
> 把判断改成了 `[rbx+04]`（最大血量）。
> 因为**系统原本的指令就在操作 **`[rbx+08]`**（当前血量），既然 **`+08`** 是合法的，那么紧挨着它前面的 **`+04`** 就绝对不可能是非法内存。**
>
